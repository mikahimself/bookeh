## Intent

**Problem:** Wishlist entries (7.2) need a list to sit on, and there is nowhere to keep one. A wishlist is a private, named list ("Me", "Christmas") that only its owner sees (FR-38, AD-1).

**Approach:** Add a private `wishlists` collection on the `people` / `locations` pattern: `ownerField()`, `name`, `nameKeyField()`, `ownerAccess`, and a database-unique `(owner, nameKey)` in the migration that creates the table. Register it, commit the migration and the regenerated types, and prove the access rules with a two-user-plus-admin integration test.

## Boundaries & Constraints

**Always:**
- `ownerAccess` from `src/access/owner.ts` (AD-1, AD-2): read, update and delete are `owner = current user` for every role, the admin included; create is any signed-in user.
- `ownerField()` and `nameKeyField()` from `src/fields`; `name` is required text with `maxLength: limits.name`.
- One name per owner, compared by `nameKey`, enforced by the database (compound unique index in the migration), not by a hook.
- Generated interface is `Wishlist` (set explicitly with `typescript.interface`).
- The migration is generated by `payload migrate:create` from a database at the latest committed migration (`20261026_071554_loans`), and `src/payload-types.ts` is regenerated, both in the same commit (AD-13).

**Never:**
- No `wishlist-entries` collection (7.2), no `lib/wishlists` service, rename, delete or `NAME_TAKEN` logic (7.5), no screens, no server actions, no open-entry count.
- No sharing fields or share collections (Phase 2–3).
- No new access or field helper; no change to ARCHITECTURE-SPINE.md (AD-1, AD-19 and the Names convention already name `wishlists`).
- No hand-edit of the generated `owner_id` foreign key. The retro's owners-cascade rule is one migration over every owned collection (sprint item `epic-6-retro-item-66`); this table joins that set.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Create own | User A creates `{ name: '  Christmas  ', owner: B.id }` through the gateway | Saved with `owner = A`, `name` as sent, `nameKey = 'christmas'`; A finds it by id and by `find` | — |
| Foreign read | User B or the admin reads A's list by `find` / `findByID` | `find` returns no docs; `findByID` throws | `NotFound` |
| Foreign write | User B or the admin updates or deletes A's list | Row unchanged, still owned by A | `Forbidden` |
| Duplicate per owner | A creates `Me`, then `me` | Second create rejected by the unique index | `ValidationError` |
| Same name, other owner | B creates `Me` after A has one | Saved for B | — |
| Blank name | `name: '   '` | Rejected on path `name` by `nameKeyField()` | `ValidationError` |

**Acceptance Criteria:**
- Given the `wishlists` collection, when a signed-in user creates a list, then its owner is the request user whatever `owner` the input carries, and its `nameKey` is the key of its `name`.
- Given user A's list, when user B or the admin reads, updates or deletes it through the gateway, then reads return nothing (`find` empty, `findByID` `NotFound`), writes fail with `Forbidden`, and the stored row is unchanged.
- Given user A has a list named `Me`, when A creates `me`, then the database rejects it; when B creates `Me`, then it is saved.
- Given a database migrated with the committed migrations, when `migrationSchema.int.spec.ts` runs, then nothing is left to push, and `wishlists` carries a unique index on `(owner_id, name_key)`.

## Design Notes

**Index name.** Payload de-duplicates compound index names across the schema in registration order; `locations` holds `owner_nameKey_idx` and `people` `owner_nameKey_1_idx`, so this one will come out as `owner_nameKey_2_idx` or similar. Accept what the generator writes; a hand rename makes `migrationSchema` see a difference.

**Owner FK.** The generator writes `ON DELETE set null` on a NOT NULL `owner_id`, like every other owned collection. The Epic 6 retro decided owners cascade, as one migration over all owned collections (item 66, still open). Doing it here alone would mean hand-editing generated SQL that the config does not express. Recorded as a residual risk for item 66 to include `wishlists`.

**Production-dump check.** The migration creates a new table and adds a nullable column to `payload_locked_documents_rels`; existing rows are untouched. Verified on a scratch database holding data; the rehearsal against a real production dump is the operator's step on the LXC.
