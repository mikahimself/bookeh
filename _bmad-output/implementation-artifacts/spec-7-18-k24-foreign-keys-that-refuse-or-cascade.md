## Intent

**Problem:** Payload generates every relationship foreign key as `ON DELETE set null`. On the 23 keys of our collections that either fails (a NOT NULL column: deleting a user, a copy with loans or a Person with loans fails with a raw database error) or quietly loses data (a concurrent entry for a deleted Person becomes the owner's own wish; a deleted author silently leaves every Book). Epic 6 retro item 66 / decision 3, Epic 7 item 74; closes the 3.15, 3.18–3.21, 6.1, 6.4, 7.1, 7.2 and 7.4 deferrals.

**Approach:** One `afterSchemaInit` hook states the delete action of every one of those keys on the Drizzle tables, and fails schema init for a `set null` key it does not list or that sits on a NOT NULL column. A generated migration applies the change. `beforeDelete` hooks on Copies, People, Books, Authors and Series turn a back-office refusal into a readable message. AD-19 states the rule.

## Boundaries & Constraints

**Always:**
- Cascade: `owner_id` on `copies`, `locations`, `loans`, `people`, `user_books`, `wishlists`, `wishlist_entries`; `created_by_id` on `books`, `authors`, `series`, `media`; `wishlist_entries.wishlist_id`.
- Restrict: `loans.copy_id`, `loans.person_id`, `wishlist_entries.for_person_id`; `book_id` on `copies`, `user_books`, `wishlist_entries`.
- Stay `set null`: `copies.location_id`, `users.default_location_id`, `books.series_id`, `books.cover_id`, `user_books.series_id`.
- `_rels` keys stay `cascade` (a `restrict` there depends on trigger order in a user delete).
- The migration is generated by `migrate:create`, never hand-edited (AD-13); CI's drift check passes against it.
- `beforeDelete` counts through `asRequestUser(req)` (AD-3, FR-48): rows the deleting user cannot read are left to the foreign key. A request without a user (scripts, system deletes) skips the hook; the key still guards.
- Services that delete in order (`removeCopies`, `deletePerson`, `mergePerson`, `deleteWishlist`, the save's Undo, the private-Book merge) behave as before.
- AD-19 states the rule and names the hook in this commit.

**Never:**
- No hand-written SQL in the migration.
- No `restrict` on `_rels` keys.
- No change to which rows services delete or in what order.

**Decision (owner rule, CLAUDE.md deferrals):** the check "verified on a restored copy of the latest production dump" needs production, which only Mika reaches. This story verifies the migration on the migration-built test database with data in every table; the production-dump check becomes an acceptance criterion of Story 7.27 in `epics.md`, in this commit.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| User delete | user with People, loans, copies, a private Book, wishlists, entries; another user holds a copy of a shared Book | all of the user's rows gone; the other copy and the shared Book stay | — |
| Back-office copy delete | copy with a loan (open or returned) | refused with a readable message | `APIError` 409, public |
| Back-office Person delete | Person with a loan or an entry, open or closed | refused with a readable message | `APIError` 409 |
| Back-office Book delete | Book with the admin's copy, user-books row or entry | refused | `APIError` 409 |
| Back-office author / series delete | used by a Book | refused (no silent strip) | `APIError` 409 |
| Unseen reference | system delete (no user) of a Person with an entry | refused by `wishlist_entries.for_person_id` | raw database error, nothing lost |
| Schema init | a `set null` key not listed, or listed on a NOT NULL column | throws at init | `Error` naming table and column |

## Implementation Notes

- Implemented in the main session from this spec; no subagent.
- `foreignKeyActions` mutates the inline `ForeignKey` objects `getTableConfig()` returns (Drizzle 0.45.2 types `onDelete` readonly, hence the cast); `extendDrizzleTable` mutates tables in place, so nothing rebuilds them after it. It runs last in `afterSchemaInit`. Besides the NOT NULL check it also fails init for any `set null` key `ON_DELETE` does not list, and for a listed key that matched none.
- Migration `20261030_122655_foreign_keys` generated by `migrate:create` and only prettier-formatted, as earlier ones: 18 keys dropped and re-added (12 cascade, 6 restrict); the 5 `set null` keys untouched. Applied on `bookeh_test` over rows left by earlier runs (loans, entries, private Books); `pg_constraint` then reads 12 `c`, 6 `r`, 5 `n` outside `_rels`. CI's drift check run locally: the new snapshot equals the committed one and the migration has no SQL. (Running it locally also reverts `src/migrations/index.ts`, as in CI; the entry was restored by hand in the generated form.)
- RESTRICT vs NO ACTION probed first on a scratch database: a user delete that cascades to both `copies` and `loans` succeeds with RESTRICT on `loans.copy_id`, since the checks queue behind the owner cascades of the same statement. The int case confirms it on the real schema.
- `refuseWhileReferenced` lives in `src/access/deleteGuards.ts`: the import rule allows collections only `src/access` and `src/fields`. It returns 409 `APIError` with `isPublic`. A request without a user skips it (scripts, the e2e seed); the key still guards.
- Authors and series count Books only, as the AC says; a user-books override naming the author (`user_books_rels`) is still stripped by the `_rels` cascade. Residual, low: overrides belong to other users, whom the admin cannot read anyway.
- `tests/e2e/seed.ts` deletes the earlier Book's loans and wishlist entries before its copies and the Book.
- Service docs restated: `deletePerson` / `mergePerson` (7.4's race now fails the delete), `deleteWishlist` (a concurrent entry goes with the list), `removeCopies`, `sharePrivateBook`.
- Production-dump check handed to Story 7.27 as an AC in `epics.md` (frozen Decision).
