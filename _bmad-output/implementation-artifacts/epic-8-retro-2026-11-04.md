## Findings

Each finding states an instance disposition and an upstream lesson. Code fixes and contract changes below are proposals, not changes applied by this retrospective.

### Cross-story review

**X1. Own-library search violates the shared-context serialization rule.**

- Source: `src/lib/shelf/searchMine.ts:68–71` uses `Promise.all` for `getEffectiveBooks(ctx, bookIds)` and `getHoldings(ctx, bookIds)`. Both reach the Payload gateway with the same request. `src/lib/payload/gateway.ts:13–18` explicitly requires calls on one context to run one at a time (AD-16). The equivalent reads in `src/lib/catalogue/lookupBook.ts:123–125` are sequential.
- Consequence: concurrent Local API operations share mutable request/transaction state outside the supported service contract. No runtime failure was observed; the phone-width title-search walk passed.
- **Instance: fix now, action 1.** Await the two reads sequentially. **Prevention:** check the operations behind parallel helpers, not just whether the page's top-level services are sequential. `scan/find/page.tsx` deliberately sequences its services, but that alone does not enforce AD-16 inside them.
- Independently identified by adversarial and edge-case lenses; consolidated here.

**X2. Search and edition Answers overwrite each other's cover-preview record.**

- Source: `src/lib/catalogue/searchBooks.ts:39–40` records a one-element preview array for each search hit. `src/lib/catalogue/coverPreview.ts:47,64–80` keys the record only by user and ISBN and replaces its URL array. `:121` resolves the requested candidate through `pickIndex`; the pre-save Answer uses candidate-indexed URLs (`src/app/(frontend)/scan/answer.ts:138–157`).
- Trigger: tab A has a multi-candidate Answer open; tab B searches the same ISBN and records its single search cover. A subsequent candidate-cover request from tab A resolves against the search array, with an out-of-range candidate falling back to index zero. It can show a cover inconsistent with the selected edition. This is source-traced, not browser-reproduced. It does not demonstrate a wrong saved edition or a privacy leak.
- **Instance: fix now, action 2.** Isolate search previews from indexed Answer previews, with an explicit preview context or equivalent server-held identity. Preserve the server-only URL and authenticated-host checks. Add one focused collision case guarding AD-10/AD-14.
- **Prevention:** when a new surface shares process state, review its key and replacement semantics against existing consumers, including separate tabs.
- Independently identified by adversarial and edge-case lenses; consolidated here.

**V1. Kirjasampo's positive production request path is bypassed by its tests.**

- Source: `tests/unit/kirjasampo.unit.spec.ts:81–87` invokes the production adapter only for a non-Finnish ISBN and asserts no request. Positive cases call `kirjasampoResults`, or the file-reading `fixtureKirjasampo` adapter. `tests/e2e/kirjasampo.spec.ts` uses that fixture adapter; `src/lib/metadata/sources/fixture.ts:81` reads recorded JSON directly. The production Finnish request is in `src/lib/metadata/sources/kirjasampo.ts:103` onward.
- Consequence: request/query/parser wiring could regress while parser, capture and browser tests still pass. This is a regression gap against Story 8.15's exact-ISBN SELECT and enrichment criteria, not evidence that the adapter currently fails. Story 8.15 records a successful live lookup, which is historical positive evidence.
- **Instance: fix now, action 3.** Stub fetch with a recorded Finnish response, invoke the actual adapter, check the generated query and resulting work/themes, and cover one request/HTTP failure returning `undefined`. No live requests in tests.
- **Prevention:** verify the production entry point as well as exported parsers; fixture-mode browser coverage cannot prove HTTP adapter wiring.
