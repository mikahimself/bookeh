## Intent

**Problem:** There is nowhere to record that a copy is lent. A loan has to be its own row, pointing at one of the user's copies and one of their People, so the copy keeps its location while lent and returned loans stay as history (FR-35, FR-36, AD-8).

**Approach:** Add a private `loans` collection: `ownerField()`, `copy` and `person` as `ownedRelation`s, and two calendar-date fields `lentOn` (required) and `returnedOn` (empty while open), both stored at 12:00 UTC. "One open loan per copy" is a partial unique index on `loans(copy)` where `returnedOn` is null, added through `afterSchemaInit` and present in the migration that creates the table (AD-19). Commit the migration and regenerated types, and prove access and constraints with an integration test that uses foreign ids (AD-17).

## Boundaries & Constraints

**Always:**
- `ownerAccess` (AD-1, AD-2): read, update and delete are `owner = current user` for every role, the admin included.
- `copy` is `ownedRelation('copies', …)` and `person` is `ownedRelation('people', …)`, both required. Neither is a `readableRelation`.
- A calendar date is stored as `<UTC date>T12:00:00.000Z` whatever time of day the write carried: `'2026-10-20'` and `'2026-10-20T23:30:00Z'` both store `2026-10-20T12:00:00.000Z` (spine, Consistency Conventions → Dates). An empty `returnedOn` stays empty.
- A `returnedOn` before `lentOn` (by UTC date) is rejected on path `returnedOn`; the same day is allowed. One-collection invariant, so a collection hook (AD-18, last bullet), on the `noLocationWhenOrdered` pattern in `Copies.ts`.
- The partial unique index is declared through the Postgres adapter's `afterSchemaInit`, because collection `indexes` cannot carry a `where` (same reason as `catalogueIndexes.ts`).
- The migration is generated by `payload migrate:create loans` from a database at the latest committed migration (`20261026_045004_people`); `src/payload-types.ts` is regenerated; both in the same commit (AD-13).

**Never:**
- No `lib/loans` service, no lend/return/Undo (6.5), no "lending date in the future" check (time-dependent, 6.5's service), no "only an owned copy" check (cross-collection, 6.5).
- No change to `removeCopies` or to copy/Person deletion (6.4, 6.3); no holdings change (6.6); no screens or actions.
- No new helper in `src/fields` and no change to ARCHITECTURE-SPINE.md: AD-8, AD-17, AD-19 and the Dates convention already describe this collection.
- No change to the generator's `ON DELETE set null` foreign keys (6.1's deferred item stays with 6.1).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Create own | A creates `{ owner: B.id, copy: A's copy, person: A's Person, lentOn: '2026-10-20' }` | Saved with `owner = A`, `lentOn = '2026-10-20T12:00:00.000Z'`, `returnedOn` null; A finds it by id and `find` | — |
| Time of day dropped | `lentOn: '2026-10-20T23:30:00.000Z'`, later `returnedOn: '2026-10-22T05:00:00.000Z'` | Stored `2026-10-20T12:00:00.000Z` and `2026-10-22T12:00:00.000Z` | — |
| Foreign copy | A creates a loan with B's copy (A's Person) | Not saved | `ValidationError` on `copy` |
| Foreign Person | A creates a loan with B's Person (A's copy) | Not saved | `ValidationError` on `person` |
| Foreign read / write | B or the admin reads, updates or deletes A's loan | `find` empty, `findByID` throws; writes refused; row unchanged | `NotFound` / `Forbidden` |
| Second open loan | A's copy has an open loan; A creates another open loan on it | Rejected by the partial unique index | `ValidationError` |
| Open after returned | A's copy has a returned loan; A creates an open loan on it | Saved; a copy may have any number of returned loans | — |
| Return before lent | Update `returnedOn` to the day before `lentOn` | Rejected; same day as `lentOn` is accepted | `ValidationError` on `returnedOn` |

**Acceptance Criteria:**
- Given the `loans` collection, when a signed-in user creates a loan, then its owner is the request user whatever `owner` the input carries, `copy` and `person` must be that user's own rows, and `lentOn` / `returnedOn` read back as their UTC date at 12:00 UTC.
- Given a copy with an open loan, when any write would give it a second open loan, then the database rejects it; returned loans never block a new one.
- Given user A's loan, when user B or the admin reads, updates or deletes it through the gateway, then reads return nothing and writes fail, and the stored row is unchanged.
- Given a database migrated with the committed migrations, when `migrationSchema.int.spec.ts` runs, then drizzle-kit has nothing to push, and `\d loans` shows the partial unique index on `copy_id` where `returned_on` is null.

## Design Notes

**Why the return-date rule is here.** The epic puts "a return date before the lending date is a field error" in 6.5's acceptance, but it is an invariant of one collection, and AD-18 puts those in the collection's hooks so the back office cannot break it. 6.5's service then gets the field error from the collection and adds only the time-dependent "lending date not in the future" check and the cross-collection "owned copy" check.

**Calendar dates.** Normalising in a field `beforeValidate` hook makes 12:00 UTC hold for every write path (service, back office, tests), and is idempotent on update, where Payload refills unsubmitted fields from the stored ISO string. Read-back is `value.slice(0, 10)`; that helper belongs to whichever story first reads a loan date (6.6), not here.

```ts
const toNoonUtc: FieldHook = ({ value }) => {
  if (typeof value !== 'string' && !(value instanceof Date)) return value
  const date = new Date(value)
  return Number.isNaN(date.getTime()) ? value : `${date.toISOString().slice(0, 10)}T12:00:00.000Z`
}
```

**Production-dump check.** The migration creates a new table and adds a nullable column to `payload_locked_documents_rels`; existing rows are untouched. The implementer verifies on a scratch database holding data (see Verification). The rehearsal on an actual production dump is the operator's step on the LXC (`deploy/restore-rehearsal.sh`, then `payload migrate`), recorded in the Auto Run Result as not run here.
