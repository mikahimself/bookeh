### Cross-story defects

- **X1. A Book that is only on a wishlist scans to a blank Scan screen.**
  - **Source:** `notInLibrary` returns null when `mine.entries.length > 0` (`scan/answer.ts:118`). `inLibrary` needs a copy, so `answerFor` falls through to `{ kind: 'scan' }` (`:333-336`). `tests/unit/answer.unit.spec.ts:420-426` pins this as intended.
  - **What happens:** 7.3 made holdings carry entries, and 7.6 and 7.14 let the frontend create them. Since then, the everyday sequence "Add to wishlist, then later scan the same book in a shop" ends on Scan with no Answer, no message and no Add to library. This also happens when the only entry is for a Person.
  - **Reproduced in the browser:** walk-through steps 01–04.
  - **Recorded:** deferred in spec-7-3:16, 109 (medium) to Epic 8's On wishlist heading (8.1/8.2, `epics.md:3117,3121`). The deferral follows the rule, but neither Epic 8 criterion says the screen must not reset silently.
  - **Disposition: Fix now** (item 1). One-line stopgap: the entry-only case returns the Not in library Answer, so Add to library saves the copy and 7.7 closes the wish. Epic 8 then replaces it with the On wishlist heading.
  - **Prevent:** P1.
- **X2. Bought on your own entry leaves your other open entries for the same Book open.**
  - **Source:** `closeEntry` calls `createCopy` and never `closeEntriesForBook` (`src/lib/wishlists/entries.ts:167-176`). Compare `saveCopy.ts:338-339`.
  - **What happens:** take a Book with an own entry on "Minulle" and another on "Joulu". Bought on "Minulle" creates the owned copy, but Book detail then shows Your copies and On wishlists: Joulu together. Screenshot `28-detail-after-bought.png`.
  - **Against the PRD:** FR-28 says "Adding a Book to the library closes the user's own open wishlist entries for it" (`prd.md:144`).
  - **Recorded:** spec-7-8:31, 110, 151 chose "only this entry", citing AD-18's wording. AD-18 (spine:251) names what `closeEntry()` calls but does not forbid the wider close, and the PRD outranks the spine.
  - **Disposition: Fix now** (decision 1, item 1). FR-28 stands as written.
- **X3. On the Not found form, the wishlist press and the library press don't block each other.**
  - **Source:** `NotFoundForm.tsx:132-141`. `AddToWishlist` gets `disabled={pending}` from the library press, but the submit Button ignores the wishlist press's pending state. Each press has its own `useSavePress` and `requestId`, and the request memory keys on kind.
  - **What happens:** with exactly one list, the wishlist press saves at once. Pressing Enter or Add to library before it returns creates a second private Book with no ISBN, and nothing merges the two.
  - **Recorded:** rejected at spec-7-14:174 because the fix is "shared busy state lifted across a server component". That holds for `NotInLibraryAnswer` but not for `NotFoundForm`, which is a client component.
  - **Disposition: Fix now**, small (item 1).
- **X4. Concurrency and edge cases, recorded or low.**
  - **Lost response:** when the Bought or Ordered response is lost, a retry gets `NOT_FOUND` and the "Not on this list" toast, so the Undo token is gone (`actions/wishlists.ts:112-122`, `EntryActions.tsx:56-79`). The copy exists and nothing is duplicated.
  - **Save Undo after Bought:** a save's Undo deletes an entry that a Bought has closed since (`entries.ts:57,331-338`). Today it can't be reached from the screen because only one toast shows at a time (`ToastProvider.tsx:37`). spec-7-6:104 gave a reason that 7.8 has since made stale.
  - **Refused list:** a `{create}` name that gets refused, or a list deleted meanwhile, fails as "Save failed" only after a counted lookup and a cover download (`saveCopy.ts:242-262`, `scan/actions.ts:173-178`; accepted at spec-7-14:204).
  - **Reopened wishes:** undoing an earlier save reopens wishes while a later copy exists (spec-7-7:96, 174).
  - **Disposition: Accept**, recorded here.
- **X5. NOT NULL foreign keys with `ON DELETE set null`, in two more tables.**
  - **Source:** `20261027_115654_wishlists.ts:15` and `20261027_125540_wishlist_entries.ts:17-20` copied the pattern that the Epic 6 retro decided to replace (item 66).
  - **Effect:** a back-office delete of a list, Book, Person or user with entries fails as a raw NOT NULL violation. No data is lost.
  - **The race:** 7.4's concurrent Person delete or merge race turns a recipient's entry into the owner's own wish (spec-7-4:16). It sits in `epic-7-context.md:72` as an open item, which is the parking that Epic 6 item 72 forbids for a deferral touching an AD (AD-18 "deletes failing on foreign keys", spine:248).
  - **Disposition: Fix now** (item 2, which is item 66, now larger).
  - **Prevent:** P2.
