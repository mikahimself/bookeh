## Intent

**Problem:** Accounts have no visibility settings, so friends (Phase 2, F8) cannot be added later without reworking the `users` schema (FR-4, D-1). Settings has no way to state them.

**Approach:** Add `profileVisibility` (`public` | `hidden`, default `hidden`) and `collectionVisibility` (`open` | `closed`, default `closed`) to `users` with a committed migration, pass them through `lib/account` (`Profile`, `ProfileChanges`, `updateProfile`), and show a Visibility group in Settings after Theme: a Profile switch public / hidden and a Collection switch open / closed that save at once. The values change nothing else in Phase 1.

## Boundaries & Constraints

**Always:**
- `src/collections/Users.ts`: both fields `type: 'select'`, `required: true`, with the defaults above — the `language` pattern. No field-level access: a user already updates only their own document, and the fields are not privileged like `roles`.
- The migration is generated by `npx payload migrate:create visibility` against `bookeh_test`, never hand-written, never applied to a dev database (AD-13). `payload-types.ts` is regenerated and committed.
- Writes go only through `lib/account`: `updateProfile` passes the two keys through untouched (no normalisation); Payload's select validation catches unknown values, and `runAction()` maps it to `VALIDATION`.
- Option tuples live in `src/lib/account/profile.ts` as exported consts typed `readonly User['profileVisibility'][]` / `readonly User['collectionVisibility'][]`, so `payload-types.ts` keeps them honest. `profileChanges.ts` validates against them (it is not a `'use client'` file, so value imports from `src/lib` are allowed); the page passes them to the client switches as props (the `ThemeSwitch` `options` precedent).
- `parseProfileChanges` accepts the two new keys only with a value from the matching tuple; anything else, extra keys included, stays `null`.
- Payload's create type requires required fields even with a default, so every `payload.create` call site adds `profileVisibility: 'hidden'`, `collectionVisibility: 'closed'`: `seedFirstUser.ts`, `tests/helpers/harness.ts`, `tests/helpers/seedUser.ts`.
- Settings: a Visibility group (`h2` like the others, key `settings.visibility`) between Theme and Sign out, holding two rows. Each row: a visible label (`text-label text-text-muted`, the email-label pattern) — Profile, then Collection — above a `TextSwitch` (same word as `aria-label`, lowercased options via `ui-case`, no `properNames`).
- Switch behaviour is the `ThemeSwitch` pattern minus the attribute write: mark the tapped option chosen at once, call `updateProfileAction({ <field>: next })`, on failure revert and report through `useReportFailure()` (toast; `UNAUTHENTICATED` → `/login?next=%2Fsettings`). No `router.refresh()` — nothing else on the page depends on the values.
- One client component `VisibilitySwitch` used twice, parametrised with the field key, label, initial value and options.
- All strings in `messages/en.json` and `messages/fi.json` under `settings`; `jsx-no-literals` and key parity hold.

**Never:** No behaviour anywhere else reads the two fields in Phase 1 — no filtering, no sharing, no admin logic. No change to `TextSwitch`, `report.ts`, `actions/account.ts` (the action already delegates to the parser and service), access rules, `prefs.ts` or `styles.css`. No new tokens. No success toast, no confirm. No `sprint-status.yaml` edit (close-out is a separate chore commit by repo convention).

## Design Notes

- **Required with defaults, like `language`.** Optional fields would type as `'public' | 'hidden' | null` and push null-handling into `Profile`; the epic fixes the defaults, so the columns are non-null from birth and existing rows are filled by the migration's default.
- **Tuples in `lib/account`, not `src/fields`.** The values are profile vocabulary, used by the parser and the page; `src/fields` is for reusable Payload field factories (Epic 3). `Users.ts` keeps literal options like it does for `language` — the generated types reconcile the two.
- **One component, two instances.** The switches differ only in field, label and options; `field` is the action payload key, so the component stays one small generic.
