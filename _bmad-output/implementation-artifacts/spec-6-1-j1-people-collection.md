## Intent

**Problem:** Loans (6.2) and, later, wishlist entries need a borrower or recipient, and there is nowhere to keep one. A Person is a private name on the user's own list, never a user account (FR-34).

**Approach:** Add a private `people` collection on the `locations` pattern: `ownerField()`, `name`, `nameKeyField()`, `ownerAccess`, and a database-unique `(owner, nameKey)` in the migration that creates the table. Register it, commit the migration and the regenerated types, and prove the access rules with a two-user-plus-admin integration test.

## Boundaries & Constraints

**Always:**
- `ownerAccess` from `src/access/owner.ts` (AD-1, AD-2): read, update and delete are `owner = current user` for every role, the admin included; create is any signed-in user.
- `ownerField()` and `nameKeyField()` from `src/fields`; `name` is required text with `maxLength: limits.name` (200, `src/fields/limits.ts`).
- One name per owner, compared by `nameKey`, enforced by the database (compound unique index in the migration), not only by a hook.
- Generated interface is `Person` (set explicitly with `typescript.interface`).
- The migration is generated by `payload migrate:create` from a database at the latest committed migration, and `src/payload-types.ts` is regenerated, both in the same commit (AD-13).

**Never:**
- No `lib/people` service, no matching, rename, merge or delete logic (6.3), no `loans` collection (6.2), no screens or Settings group (6.13), no server actions.
- No new access helper or field helper; no change to ARCHITECTURE-SPINE.md (AD-1, AD-19 and the Names convention already name `people`).
- No accent folding or locale-specific casing in the key.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Create own | User A creates `{ name: '  Liisa  ', owner: B.id }` through the gateway | Saved with `owner = A`, `name` as sent, `nameKey = 'liisa'`; A finds it by id and by `find` | — |
| Foreign read | User B or the admin reads A's Person by `find` / `findByID` | `find` returns no docs; `findByID` throws | `NotFound` |
| Foreign write | User B or the admin updates or deletes A's Person | Row unchanged, still owned by A | `Forbidden` |
| Duplicate per owner | A creates `Liisa`, then `liisa` | Second create rejected by the unique index | `ValidationError` |
| Same name, other owner | B creates `Liisa` after A has one | Saved for B | — |
| Blank name | `name: '   '` | Rejected on path `name` by `nameKeyField()` | `ValidationError` |

**Acceptance Criteria:**
- Given the `people` collection, when a signed-in user creates a Person, then its owner is the request user whatever `owner` the input carries, and its `nameKey` is the key of its `name`.
- Given user A's Person, when user B or the admin reads, updates or deletes it through the gateway, then reads return nothing (`find` empty, `findByID` `NotFound`), writes fail with `Forbidden`, and the stored row is unchanged.
- Given user A has a Person named `Liisa`, when A creates `liisa`, then the database rejects it; when B creates `Liisa`, then it is saved.
- Given a database migrated with the committed migrations, when `migrationSchema.int.spec.ts` runs, then drizzle-kit has nothing to push, and the table carries a unique index on `(owner_id, name_key)`.

## Design Notes

**Index name.** Payload names a compound index from its columns and de-duplicates across the whole schema in registration order. `locations` already holds `owner_nameKey_idx`, so the `people` index will be generated as `owner_nameKey_1_idx`. That is accepted: the column pair and uniqueness are what matter, and the migration records the name. Do not hand-rename it in the SQL, or `migrationSchema` will see a difference.

**Production-dump check.** The epic requires schema changes to be applied to a restored copy of the latest production dump before merge. The migration only creates a new table and adds a nullable column to `payload_locked_documents_rels`, so existing rows are untouched. The implementer verifies on a scratch database that already holds data (see Verification). The rehearsal against an actual production dump is the operator's step on the LXC (`deploy/restore-rehearsal.sh`, then `payload migrate`), recorded in the Auto Run Result as not run here.
